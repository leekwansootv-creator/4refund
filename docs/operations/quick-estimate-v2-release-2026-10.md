# 견적 v2와 뉴스 홈페이지 운영 전환

## 범위와 승인 경계

2026-10-28 사용자는 견적 v2 배포 조건을 해결한 뒤 실제 뉴스 3건이 홈페이지에 보이도록
배포할 것을 요청했다. 실제 접수·알림 검증은 먼저 대상·건수·수신자·시험 데이터 처리 범위를
제시한다. 운영 설정에는 소유 계정의 표시명과 승인된 두 알림 주소를 사용한다.
주소·문서 ID·배포 URL·완전한 payload는 이 문서와 Git에 기록하지 않는다.

기준 main은 뉴스 PR #54의 `fa2fc417d0f9c539371a8b8d9542ed1a8ea3df92`다.
이전 작업 브랜치와 원본 checkout을 보존하고 `codex/quote-v2-release`에서 진행한다.
현재 공개 Pages 배포는 `c5b468b70afff43dc13a839f791442b9f58fdf36`이며,
배포 실행은 `33858034809`다. 새 계정의 준비 환경과 기존 운영 자산을 혼동하지 않는다.

## 사전 읽기 점검

- 실제 준비 프로젝트의 저장 코드가 기준 main의 견적 bundle과 개행 정규화 후 일치했다.
- 출처 표식은 `2`, 원본 헤더 29열·상담 헤더 18열을 Sheet UI에서 읽었다.
- 준비 manifest는 Sheets·실행자 이메일 확인만 허용하며 접근은 본인으로 제한돼 있었다.
- 배포 관리의 활성·보관 배포는 모두 없고, 트리거도 0개다.
- 담당자와 알림 수신자는 비어 있었다. 두 수신자 지원은 이번 변경에서 추가한다.
- 뉴스 탭을 추가한 문서에는 기존 세 탭 전용 빈 시트 초기화 함수를 재실행하지 않는다.
  구조·보호·행 수만 읽는 별도 점검문을 사용하고 준비 파일은 보존한다.
- 읽기 전용 구조 검사에서 원본·상담의 데이터 행은 모두 0개이며 헤더, 출처 schema `2`,
  소유자 전용 보호 범위가 일치했다. 두 뉴스 탭도 유지됐다. 임시 점검 함수는 실행 후 제거했다.
- 승인된 담당자·수신자 설정을 저장한 뒤 `checkQuickEstimateOperatorSettings()`는 두 항목을
  `configured`, 전체 `ready: true`로 반환했다. 이는 형식 검사이며 실제 메일 전달 검증은 아니다.
- 이전 공개 실행의 archive 목록은 비어 있어, 공개 사이트의 파일을 별도 로컬 복구본으로
  내려받았다. 공개 HTML·JS·CSS·글꼴·이미지 195개, 19,669,773바이트와 SHA-256 목록이다.
  저장 후 195개 해시를 다시 계산한 결과 불일치는 0개다. 로컬 브라우저에서 조회 팝업,
  제조업 30명 계산 결과 표시, 상세 신청 폼 진입을 확인했고 신청은 전송하지 않았다.
  새 형식 archive를 사용한 자동 rollback 대상은 아니므로 최초 전환 복구 절차가 별도로 필요하다.

## 로컬 검증

Node 22.15.0, npm 10.9.2, uv 0.13.4에서 실제 저장 E2E를 끈 상태로 `npm run check`를 실행했다.
이번 실행 결과는 Node 검사 27개, Vitest 42파일·348개, 수집 서비스 Python 46개,
Playwright 45개 통과·실연동 5개 생략이다. 포맷·lint·타입·아키텍처·주석·bundle 검사와
정적 빌드도 통과했다. `git diff --check`와 추가 문서 포맷 검사도 통과했다.

두 수신자, 기존 단일 수신자, 대소문자가 다른 중복, 잘못된 주소 혼합 시 전체 거절을 회귀
검증했다. 메일 호출은 두 주소를 한 번에 전달하며 수신자별 부분 재시도는 추가하지 않았다.
이 결과는 Google 메일 수신·quota·실제 접수·공개 홈페이지 배포 성공을 증명하지 않는다.

## 최초 전환 전 남은 운영 검증

- 견적 앱의 추가 OAuth scope와 소유자 실행·익명 POST 배포 승인을 받은 뒤 활성화한다.
- 운영 문서의 개인정보 보유·파기 조건을 검증한다. 실제 접수·뉴스 문서와 분리한 시험 문서에
  가짜 보유·파기 대상만 넣고 보유 대상의 새 파일 이동, 읽기 대조, 공유 범위와 참조 변경을
  검증하는 절차를 준비한다. 영구 삭제는 정확한 시험 파일을 지정해 실행 시 확인받는다.
  기존 고객 문서·뉴스·버전 기록을 이 시험 대상으로 사용하지 않는다.
- 공개 복구본과 digest는 이 작업의 로컬 증적 폴더에 보관했다. 최초 전환 전 복구 실행 경로와
  보관 담당자를 운영 기록에 확정한다. 이후 첫 성공 v2 전체 archive는 90일 Actions 보관과
  별도 로컬 장기 보관을 함께 유지한다. 복구 시 이미 공개한 고정 위젯 자원을 제거하지 않는다.
- 모바일 viewport 검사와 실제 모바일 기기 검증을 구분한다. 실제 기기의 수신·입력 동작은
  아직 확인되지 않았다.

## 실제 연동 시험 계획 — 실행 전 확인 필요

대상은 사용자 지정 새 계정의 준비 문서와 새 견적 웹앱이다. 기존 운영 endpoint와 기존 고객
행은 시험 대상이 아니다. 모든 고객 입력은 `운영전환검증` 접두어, 가짜 이름, `.test` 이메일과
시험 전화번호를 사용하며 실제 고객 연락처를 사용하지 않는다. SMS·전화는 발생하지 않는다.

| 구분              | 신규 저장 상한 | 검증                                                          |
| ----------------- | -------------- | ------------------------------------------------------------- |
| 이전 요청 계약 v1 | 1건            | 구형 요청·규칙 호환, 확장 시트 저장                           |
| 홈페이지 v2       | 2건            | 데스크톱/모바일, 선택 마케팅 동의·미동의, 화면·저장 금액 일치 |
| 외부 삽입 v2      | 2건            | 서로 다른 시험 origin의 출처 분리                             |
| 홈페이지 공개 후  | 1건            | 실제 배포 화면의 최종 신청·저장·알림 확인                     |
| 같은 요청 재시도  | 추가 0건       | 최대 2회, 같은 ID·payload·lead ID, 중복 행·중복 알림 없음     |
| 잘못된 금액·출처  | 추가 0건       | 최대 2회, 오류 응답과 행 수 유지                              |

신규 시험은 원본·상담 각 최대 6행이다. 정상 접수 알림은 승인된 두 주소에 각각 최대 6통,
총 12통이다. 누락·실패 점검을 실제로 검증해야 할 경우 운영 확인 메일을 두 주소에 1통씩
추가하는 상한은 별도로 포함하여 **총 14통 이하**로 제한한다. 제한에 도달하면 재시도를 멈춘다.
메일 본문에는 고객 이름·회사·연락처·금액을 넣지 않는다. 수신자 두 주소는 서로 볼 수 있다.
받은편지함 확인은 이 작업의 발신자·제목·시간 범위로 제한한다.

완료 후 새로 만든 시험 ID만 식별해 사유·ID·처리일을 기록한 다음 해당 원본·상담 행만
제거하는 안을 제시한다. 기존 행·뉴스·codebook·보호·버전 기록은 삭제하지 않는다.
일반 행 삭제는 버전 기록의 영구 파기를 의미하지 않는다.

## 활성화와 배포 순서

1. 로컬 코드·회귀 검사와 구조 읽기 결과를 확인한다.
2. 담당자·두 수신자·공식 홈페이지 origin을 Script Properties에 저장하고 읽어 확인한다.
3. 메일 발송·설치형 트리거 관리 권한 추가와 새 웹앱의 익명 POST 공개 범위를 실행 시 확인한다.
4. 승인 후 운영 manifest와 setup을 적용하고 편집·시간 트리거가 각각 하나인지 확인한다.
5. 메일 잔여 수신자 quota, 새 배포 코드와 Sheet 계약을 읽어 확인한다.
6. 승인한 시험만 실행하고 행·출처·중복·알림 도착을 대조한다.
7. 개인정보 고지·보유/파기 운영·복구 경로·Pages 환경과 공개 조건의 남은 차이를 확인한다.
8. 증적이 충족된 뒤 endpoint secret과 준비 변수를 설정하고 PR 검수·병합, 수동 release,
   공개 manifest·기사 3건·이미지·링크·견적 흐름을 검증한다.

현재 이 문서는 계획과 사전 점검 기록이다. OAuth 확대·setup·실제 접수·메일 수신·운영 배포를
완료한 것으로 해석하지 않는다. 각 결과는 실제 실행 후 갱신한다.
