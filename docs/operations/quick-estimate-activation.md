# 새 접수 환경의 설정 입력과 활성화

## 지금 입력하지 않아도 되는 두 값

2026-10-23 사용자 결정에 따라 담당자와 신규 접수 알림 수신자는 추후 입력한다. 코드나 홈페이지를 수정하지 않고 새 Apps Script 프로젝트의 **프로젝트 설정 → 스크립트 속성 → 스크립트 속성 수정**에서 설정한다. 기존 계정 프로젝트와 혼동하지 않도록 miningdev8의 새 준비 프로젝트인지 먼저 확인한다.

| 속성 이름                               | 나중에 입력할 값                                                  | 미입력·변경 시 동작                                                                   |
| --------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `QUICK_ESTIMATE_DEFAULT_ASSIGNEE`       | 실제 상담 담당자 이름. 30자 이내 한글·영문 이름                   | 새 상담은 미배정(빈 셀). 변경은 새로 투영되는 행부터 적용하며 기존 담당자는 유지      |
| `QUICK_ESTIMATE_NOTIFICATION_RECIPIENT` | 신규 접수 및 운영 점검 알림을 받을 이메일 최대 두 주소, 쉼표 구분 | 미입력·형식 오류 시 발송하지 않고 실패 집계. 세미콜론·줄바꿈·빈 항목·표시 이름은 거절 |

실제 이름이나 메일 주소를 저장소·PR·이슈에 넣지 않는다. `미정`, 샘플 이름, `example.com` 주소를 운영 값으로 대신 채우지 않는다. 시트 소유 계정, 기본 상담 담당자, 알림 수신자는 서로 다른 개념이며 자동으로 같은 사람으로 정하지 않는다.

2026-10-28 사용자는 소유 계정과 추가 계정 두 곳의 수신을 요청했다. 기존 한 주소 설정도 그대로 지원하며,
앞뒤 공백과 대소문자만 다른 중복은 한 번만 수신하도록 정규화한다. 전체 목록 검증 후 MailApp 호출 한 번에
전달하므로 일부 주소만 선발송하지 않는다. 수신자들은 메일의 받는 사람 목록을 서로 볼 수 있다.
Google 메일 quota는 메시지 수가 아닌 수신자 수를 기준으로 소모되므로 두 주소 설정의 용량을 별도로 확인한다.
주소 원문은 설정 검사 결과나 실패 로그에 포함하지 않는다.

## 저장한 값을 안전하게 확인

1. 두 속성을 입력하고 저장한다. 기존 시트 ID와 출처 schema 속성은 변경하지 않는다.
2. 편집기 함수 목록에서 `checkQuickEstimateOperatorSettings`를 실행한다.
3. 실행 로그에서 아래 결과를 확인한다. 이름·주소 원문은 출력하지 않는다.

```json
{
  "ready": true,
  "defaultAssignee": "configured",
  "notificationRecipient": "configured"
}
```

`missing`은 미입력, `invalid`는 형식 오류다. 이 함수는 Script Properties를 읽기만 하며 시트 쓰기, 트리거 생성, 메일 발송, 접수 요청을 하지 않는다. `ready: true`도 Google 권한·시트 정합성·메일 도착·공개 승인을 의미하지 않는다.

`setupQuickEstimateStorage`는 두 설정이 준비되지 않으면 `operator_settings_not_ready`로 시트 쓰기·트리거 생성 전에 중단한다. 이 사전 검사는 웹앱 전체의 접수 차단 스위치는 아니다. 실제 공개는 아래 절차가 끝난 뒤에 진행한다.

## 설정 입력 이후의 실행 순서

1. **코드와 새 자산 확인:** 병합된 `Code.gs`, 대상 시트 ID, 소유자, 공유 범위를 대조한다. 이미 준비한 29/18열·schema `2`를 읽어 확인한다. 빈 시트 준비 함수를 업무 데이터가 있는 시트에 다시 실행하지 않는다.
2. **권한과 트리거:** 운영 manifest의 메일 발송·설치형 트리거 권한을 확인하고 승인받는다. setup 이후 편집·정기 점검 트리거가 각각 한 개만 있는지 확인한다. 준비 단계에서 승인한 Sheets·이메일 확인 두 권한만으로 이 단계를 완료했다고 보지 않는다.
3. **웹앱:** 새 계정이 실행하는 웹앱으로 배포한다. 익명 요청 허용은 폼 접수용 코드 접근이며 Google 시트를 공개 공유하는 설정이 아니다. 발급 URL은 비공개 운영 설정에만 보관한다.
4. **가짜 데이터 실연동:** 새 시트·시험 건수·수신자·시험 행 처리 방법을 명시한 뒤 승인된 범위만 실행한다. 홈페이지 v1/v2, 두 제휴 origin, 같은 ID 재시도, 잘못된 출처, 원본/상담 동기화와 알림을 확인한다. 새 주소의 지원 계약을 검증하기 전 홈페이지 주소를 바꾸지 않는다.
5. **공개 조건:** 개인정보 고지, 모바일 실기기, 제한값·quota, 전체 복구본·archive 보관, GitHub Pages 설정과 운영 증적을 확인한다.
6. **공개와 전달:** [출시·복구 절차](quick-estimate-embed-release.md)로 새 주소를 빌드에 포함해 공개한다. 실제 공개본에서 생성한 [제휴사 전달 묶음](../engineering/quick-estimate-embed-partner-handoff.md)을 제공한다.

설정 입력 전에는 실제 접수·알림·운영 트리거·웹앱·홈페이지 주소 전환을 완료 상태로 표시하지 않는다. 이름·수신자 미정 자체는 로컬 코드, 회귀 테스트, 배포본·롤백 검증과 제휴 전달 템플릿 준비를 막지 않는다.

## 보안 유지보수와 현재 공개 준비

2026-10-23 보안 업데이트는 Next.js/ESLint config `16.4.2`, Vitest `4.1.12`, Vite `8.1.6`과 호환 전이 의존성을 적용한다. npm 10.9.2의 peer resolver 오류는 Vitest 버전을 동일하게 고정하는 override로 해결했고 정상 `npm ci`로 확인했다. `--force`, `--legacy-peer-deps`나 보안 검사 제외는 사용하지 않았다.

이 날짜의 audit는 전체 16건(critical 1, high 13, moderate 2)에서 **high 5건**으로 감소했다. 운영 의존성 검사(`npm audit --omit=dev`)는 0건이다. 전체 검사는 아직 성공이 아니며 5건은 `eslint-config-next → @next/eslint-plugin-next → fast-glob → micromatch → braces` 경로에 집계된다. [braces 보안 공지](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)는 현재 수정 버전을 제시하지 않는다. lint의 로컬 glob 처리 경로이며 홈페이지 입력을 이 경로에 전달하지 않는다. [보안 후속 이슈 #50](https://github.com/leekwansootv-creator/4refund/issues/50)에서 수정 버전 또는 upstream 의존성 교체를 추적하고 lockfile과 품질 검사를 함께 갱신한다. framework 14로 내리는 자동 제안은 적용하지 않는다.

GitHub 읽기 점검에서는 Pages가 기존 custom domain·HTTPS·workflow 방식을 사용하고, `github-pages` 환경에 branch 정책이 있지만 필수 승인자 규칙은 없었다. 접수 URL secret의 최종 수정일은 2026-08-07이었다. secret 값은 읽을 수 없으므로 새 주소라고 추정하지 않는다. 연결 계정에는 push 권한이 있고 admin 권한은 없었다. 새 주소 설정과 환경 보호 변경은 해당 설정 권한으로 수행한 뒤 읽어 확인해야 한다. 이번 점검은 설정을 변경하지 않았다.

## 이번 로컬 검증과 남은 확인

2026-10-23 Node.js 22.15.0 / npm 10.9.2에서 정상 `npm ci` 후 `npm run check`를 실행했다. 도구 테스트 24개, Vitest 34개 파일 277개, Chromium E2E 36개가 통과했고 실제 Google 저장 검사 5개는 건너뛰었다. 포맷·lint·타입·구조·주석·Apps Script artifact와 정적 빌드도 통과했다. 이는 이번 변경으로 실행한 결과이며 이전 준비 결과를 재사용한 수치가 아니다.

테스트 전용 endpoint와 `/release-check` 경로에서 `1.0.0-security.1 → 1.0.0-security.2 → 1.0.0-security.1` 전환을 별도 로컬 artifact 세 개로 만들었다. 각각 무결성을 확인하고 1440px·375px에서 기본 채널, 모든 고정 release, 홈페이지·조회 전용 데모를 확인했다. 업데이트·롤백 후에도 직전 홈페이지 HTML의 자원 로딩이 통과했고 POST·누락 자원·브라우저 오류는 모두 0건이었다. 이 artifact는 미커밋 변경과 시험 endpoint를 포함한 검증용이며 공개용으로 재사용하지 않는다.

새 미배포 Apps Script의 코드 저장 및 읽기 전용 확인 결과는 [신규 환경 준비 기록](quick-estimate-miningdev8-preparation.md#운영자-설정을-추후-입력하도록-준비)에 남겼다. 실제 모바일 기기, 새 웹앱의 v1/v2 접수·메일·trigger, 운영 quota와 공개 주소의 설치 코드는 아직 검증 전이다. 두 설정 입력 후 위 활성화 순서로 진행한다.
