# 견적 v2와 뉴스 홈페이지 운영 전환

## 범위와 승인

2026-10-28 사용자는 견적 v2의 운영 조건을 확인하고 뉴스 3건이 표시되도록 홈페이지 배포까지
요청했다. 새 계정의 메일 발송·설치형 트리거 권한, 소유자 실행·익명 접수 웹앱을 승인했다.
가짜 신규 접수 최대 6건, 중복·오류 요청 최대 4회, 승인된 두 주소로 총 14통 이하의 알림,
시험 메일 확인과 이번 시험 행 정리도 승인했다. 실제 고객·뉴스·기존 버전 기록은 보존한다.

주소·문서 ID·배포 URL·완전한 payload는 이 문서와 Git에 기록하지 않는다. 승인 계정의 표시명을
상담 담당자로 사용하고 두 알림 수신자는 Script Properties에서 관리한다.

활성화 기준은 PR #55 병합 `14b9f4601ae387780a5e1869676b7a2b3bc74781`이다.
이전 작업 브랜치와 원본 checkout을 보존하고 `codex/quote-v2-activation`에서 후속 검증한다.
전환 전 공개 Pages는 `c5b468b70afff43dc13a839f791442b9f58fdf36`, 실행 `33858034809`다.

## 운영 서버 활성화 확인

- 저장 코드가 PR #55의 견적 bundle과 개행 정규화 후 일치한다.
- 웹앱 version 1을 2026-10-28 13:22 KST에 배포했다. 실행 주체는 소유자, 접근은 모든 사용자다.
- Sheets·실행자 이메일 확인에 메일 발송·설치형 트리거 관리 scope가 추가됐다.
- `setupQuickEstimateStorage()` 결과 신규 문서 생성 없이 기존 지정 문서를 사용했다.
  편집 트리거 `onEditQuickEstimateConsultation`과 30분 시간 트리거
  `runQuickEstimateOperationsCheck`가 각각 1개 설치됐다.
- 원본 29열·상담 18열과 출처 schema `2`, 소유자 전용 보호 범위를 읽어 확인했다.
  새 계정에서 이미 준비된 확장 구조를 사용했으므로 기존 고객 자료 migration은 실행하지 않았다.
- 실제 운영 문서의 공유는 소유자에게만 제한돼 있다. 뉴스 두 탭·codebook·보호 범위는 보존했다.
- 담당자·두 수신자·공식 홈페이지 origin을 저장했고 설정 검사와 실제 메일 도착을 각각 확인했다.
- 임시 설정·시험 함수는 실행 후 제거했다. 저장된 Code.gs를 다시 복사해 생성 bundle과 비교했다.

## 실제 접수와 알림 검증

모든 입력은 가짜 회사명·이름·시험 전화번호·`.test` 이메일이다. 운영 데이터의 별도 export는
하지 않았다. 로컬 증적에는 이번 가짜 시험 payload와 요청·접수 ID만 남긴다.

| 구분                            | 실행 결과 | 증거와 한계                                                       |
| ------------------------------- | --------- | ----------------------------------------------------------------- |
| 구형 요청 v1 1건                | 성공      | v1 계산 규칙, 29열 저장, 18열 상담 투영, `legacy_unknown` 출처    |
| 홈페이지 v2 데스크톱 1건        | 성공      | 실제 Chrome 1280px, 마케팅 미동의, 화면 4,610,000원과 저장값 일치 |
| 홈페이지 v2 모바일 viewport 1건 | 성공      | 실제 Chrome 375px, 마케팅 동의, 화면 4,660,000원과 저장값 일치    |

13:29 KST 기준 신규 5건·추가 요청 3회이며 원본과 상담 목록은 각각 정확히 5행이다.
홈페이지 조회·상세 폼 진입에서 POST 0건, 최종 신청에서만 전송을 확인했다.
로컬 주소는 공식 홈페이지 origin이 아니므로 홈페이지 시험의 출처 origin은 `null`,
method는 `unknown`이다. 공식 URL의 `self_location`은 배포 후 최종 1건에서 확인한다.
외부 출처 2건은 실제 제휴 사이트 브라우저 시험으로 표시하지 않는다.

두 수신함에서 각각 5통, 총 10통을 확인했다. 본문은 신규 접수 안내와 시각만 담고 고객 이름,
회사, 연락처, 금액을 포함하지 않았다. 실제 SMS·전화·고객 연락은 하지 않았다.
신규 1건과 추가 요청 1회, 수신자 전달 최대 4통의 승인 여유가 남아 있다.
이번 시험 ID·사유·처리일을 대장에 기록한 뒤 원본·상담의 해당 행만 정리한다.
행 삭제는 버전 기록의 영구 파기를 뜻하지 않는다.

## 제한값과 모바일 확인

초기 Google 잔여 메일 quota는 수신자 100명분, 정상 시험 5건 이후 90명분이었다.
사용자는 초기 접수 상한 40건/일을 승인했고 13:41 KST에 다음 값을 저장 후 읽어 확인했다.

```json
{ "minute": 10, "daily": 40, "contactHourly": 3 }
```

이는 모든 사이트가 공유하는 UTC 고정 구간 접수 제한이다. 정상 알림 80명분과 점검 여유를
고려한 초기 운영값이며 측정된 최대 처리량은 아니다. Google quota의 회복 시점과 UTC 일 경계가
같다고 가정하지 않는다. 오류·quota 부족 시 상담 목록과 운영 점검 기록을 확인한다.

2026-10-28 사용자가 ngrok 미리보기를 실제 휴대폰에서 열어 기사 3건과 조회 → 결과 → 상세
견적 폼이 정상 표시됐다고 확인했다. 기종·브라우저는 제공되지 않았다. 사용자의 확인은
실기기 표시·입력 흐름에 한정되며 최종 신청은 누르지 않도록 안내했다.
자동 viewport 검사와 사용자의 실기기 확인을 구분한다.

## 보유·파기 절차 시험

실제 접수·뉴스 문서와 별개로 가짜 데이터 전용 원본과 보유본을 만들었다.
원본에는 KEEP 1행·DELETE 1행만 넣었고, 새 보유본에는 KEEP 1행만 옮겼다.
두 문서가 소유자에게만 공개된 상태와 시험용 참조 변경 후 1행 readback을 확인했다.
실제 접수 문서 참조는 바꾸지 않았다.

사용자가 정확히 지정한 시험 원본 1개의 영구 삭제를 실행 시 승인했다.
휴지통 이동 후 해당 파일만 완전 삭제했고 원본 URL의 삭제 안내와 보유본 1행을 다시 확인했다.
보유본과 검증 기록은 보존한다. 이 결과는 Google 내부 백업이나 모든 복사본의 소거를 증명하지
않으며 실제 고객 문서·뉴스·버전 기록을 삭제한 시험이 아니다.

## 최초 전환의 복구 준비와 보관

기존 공개 실행의 Actions archive 목록이 비어 있어 공개 파일 195개, 19,669,773바이트를
저장소 밖에 보존했다. 파일별 SHA-256을 다시 계산해 불일치 0개를 확인했다.
원본 ZIP SHA-256은 `87270e8780607fd4483a217cb26d601f6db36649558698e696699633a28f3347`다.
원본은 변경하지 않으며 새 형식 자동 rollback의 입력으로 사용하지 않는다.

이전 홈페이지 소스 `c5b468b`를 별도 폴더에서 lockfile대로 설치하고, 검증한 새 접수 URL로
다시 빌드했다. 새 v2 전체 로컬 후보 위에 이전 홈페이지를 조합하되 고정 `1.0.0` 버전과
현재·이전 `_next/static/` 바이트를 보존한 복구 후보를 만들었다. 같은 경로의 다른 바이트는
거절하고 manifest를 다시 봉인했다. 운영 endpoint 일치·전체 hash·고정 버전 보존 검사가 통과했다.
1440px/375px에서 이전 홈페이지·직전 홈페이지의 열린 탭·자동 채널·고정 버전·조회 전용 demo를
검사했고 POST 0, 누락 자원 0, 브라우저 오류 0이었다. 실제 복구 공개는 하지 않았다.

복구 시에는 다음 순서를 따른다.

1. 실제 공개 run의 전체 archive와 digest를 먼저 확보하고 공개본과 대조한다.
2. 위 복구 조립을 **그 실제 archive** 기준으로 새 폴더에서 다시 수행한다. 로컬 연습 후보를
   실제 공개본인 것처럼 업로드하지 않는다. 이미 공개한 고정 버전과 정적 자원을 전부 보존한다.
3. 운영 endpoint·hash·직전 digest와 브라우저 검사를 다시 통과시킨다. 새 서버·29/18열은 유지한다.
4. 첫 legacy 복구는 일반 `rollback_run_id`가 아닌 별도 검증된 archive 업로드가 필요하다.
   복구 승인과 같은 Pages main 보호·현재 공개 digest 확인을 거친 업로드 절차로 실행한다.
   원본 구형 ZIP의 단독 업로드, secret만 바꿔 과거 HTML의 주소가 바뀌었다고 간주하는 작업은 금지한다.
5. 첫 성공 v2 전체 archive부터는 수동 workflow의 정상 rollback 대상으로 보관한다.

로컬 보관 책임은 이번 작업을 승인한 저장소 운영자이며 현재 집 PC의 작업별 증적 폴더에
원본·복구 후보·manifest·검사 로그를 함께 남긴다. 첫 공개 성공 후 전체 Actions archive와
SHA-256도 같은 폴더에 다운로드한다. Actions 90일 보관만 장기 보관으로 간주하지 않는다.
구형 소스 설치 audit는 12건(중간 2·높음 9·심각 1)을 보고했다. 이는 비활성 복구 소스의
의존성 결과이며 새 운영 소스의 보안 검사 통과로 해석하지 않는다. 복구 공개 전 별도 검토한다.

## 배포 검사 도구 수정과 검증

실제 뉴스 피드가 설정된 전체 후보에서 `test:embed-release`가 뉴스 GET을 예상 밖의 외부
요청으로 차단해 실패하는 문제를 재현했다. 검사 도구는 `EMBED_BROWSER_NEWS_API_URL`의
정확한 GET에만 기사 3건의 모의 응답을 제공한다. 나머지 외부 요청과 모든 POST 차단은 유지한다.
카드 수·원문 링크도 검증하며 workflow는 기존 공개 뉴스 변수를 검사에 전달한다.
실제 뉴스 API 가용성과 데이터는 이 모의 검사와 별도로 검증한다.

수정 후 실제 배포 설정으로 만든 로컬 후보의 전용 브라우저 검사는 통과했다.
복구 후보와 직전 홈페이지 자원 검사도 통과했다. 이번 후속 변경에서 Node 22.15.0·npm 10.9.2·uv 0.13.4로 전체 `npm run check`를 다시 실행했다. 포맷·lint·타입·아키텍처·주석·bundle·정적 빌드가 통과했고, Node 검사 27개·Vitest 42파일 348개·Python 46개·Playwright 45개가 통과했다. 일반 실연동 E2E 5개는 비활성화했다. 변경 문서 추가 포맷 검사와 `git diff --check`도 통과했다.

## 공개 전후 점검

- GitHub `github-pages` 환경의 허용 branch는 `main` 하나다. required reviewer는 없으므로
  환경 이름을 별도 사람 승인으로 설명하지 않는다.
- 최초 Embed release 실행 이력은 0건이다. 공개 manifest의 404를 수동 공개 직전에 다시 확인한다.
- 실제 검증한 접수 endpoint를 GitHub secret에 반영하고, 운영 확인 완료 후 준비 변수를 설정한다.
- PR 검사·검수·병합 후 `main`의 수동 release로 공개한다. PR 병합만으로 자동 공개되지 않는다.
- 공개 후 manifest digest·기사 3건·이미지·원문 링크·반응형을 확인한다.
- 남겨 둔 최종 가짜 신청 1건의 공식 출처·저장·메일을 확인하고 승인된 시험 행만 정리한다.

이 기록의 공개 후 항목은 실행 전까지 완료로 간주하지 않는다. 별도 기사 수집 서비스의 호스팅과
관리 사이드바 자동 추출 전체 운영은 이번 게시 3건 공개 검증과 구분한다.
