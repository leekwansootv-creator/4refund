# 선조회 플로우 출시 검증 기록

## 상태

RF-PR1~3은 전용 milestone에 병합됐다. RF-PR4는 브라우저 검증과 실제 저장 대조 준비 단계다. **실제 저장 검증과 RF-PR5 공개 조건은 아직 충족하지 않았다.** main 반영·운영 배포 완료로 해석하지 않는다.

## 검증 환경과 구분

- 런타임 기준: RF-PR3 merge `4193550eb3aa65ab281ae4c73733958126bb4f8c`, 검증 HEAD `93a3d46fe5faa04d94247547027a8e59e5c26bc5`.
- 일반 검증: 로컬 정적 export, Chromium, 테스트 전용 endpoint 식별자. POST는 모두 가로채 실제 저장·알림을 생성하지 않는다.
- 화면 범위: 데스크톱 1440px, 모바일 375px, 200% 확대에 대응하는 720×450 CSS viewport, reduced motion, native dialog 키보드 포커스와 내부 스크롤. 실제 브라우저 메뉴의 확대 조작과 스크린 리더 검증은 별도 미검증이다.
- 실제 저장: 승인된 endpoint·Sheet·알림 접근이 확보된 경우에만 별도 실행한다. 로컬 설정의 URL 존재는 승인된 테스트 환경의 증거가 아니다.
- 자격 증명·endpoint 값·Sheet ID·연락처·완전한 payload는 이 문서나 PR에 기록하지 않는다.

## 일반 검증 기록

RF-PR3에서 `npm run check`와 `git diff --check`가 통과했다. 검사 도구 7건, Vitest 208건, 일반 E2E 18건 통과, live 5건 skip이다. RF-PR4에서 추가한 브라우저 시나리오의 실제 실행 결과는 출하 기록에 추가한다.

RF-PR4에서 `npm run test:e2e:run -- e2e/quick-estimate-result-first.spec.ts` 7건이 통과했다. 별도 endpoint 없는 정적 빌드도 Chromium 1440px·375px에서 계산·재조회·문의 이동, POST 0회, 페이지 오류 0건을 확인했다. 이 빌드의 접수 불가 결과 화면을 캡처해 확인했으며 실제 외부 저장은 발생시키지 않았다.

| 범위      | 확인 내용                                               |
| --------- | ------------------------------------------------------- |
| 조회 경계 | 조건·조회·재조회·신청 진입·입력·이전 이동의 제출 0회    |
| 신청 경계 | 필수 연락처·동의 뒤 신청 1회, 마케팅 미동의 허용        |

| 복구      | 같은 payload 재시도, 불확실성 유지, 명시적 닫기 경고    |
| 완료      | 성공 응답 전 완료 없음, 완료 후 재제출 없음             |
| 접근성    | 각 화면 axe, 긴 동의 전문·스크롤·포커스·확대            |
| 접수 중   | Escape·닫기·입력·이전 이동 차단                         |

### 발견사항과 수정

- 초기 업종 안내와 입력 placeholder의 명암 대비가 2.09:1로 axe 기준을 충족하지 못했다. 글자색을 `#666`으로 조정했다.
- 빈 연락처에서 동의 전문으로 이동할 때 blur 오류가 후속 버튼을 밀어 첫 클릭이 누락됐다. 연락처 필드에 오류 안내 공간을 예약하고 첫 클릭으로 전문이 열리는 브라우저 회귀 검증을 추가했다.
- CSS `zoom: 2`는 `vh` 영역을 줄이지 않아 브라우저 확대와 다른 clipping을 만들었다. 확대 대응 검사는 가용 CSS viewport를 절반으로 줄이는 방식으로 정정했다. native dialog의 브라우저 주소창 이동과 배경 UI 포커스 이탈도 구분한다.

## 실제 저장 대조 절차 — 미실행

1. 문서의 승인 운영 계정에서 테스트용 Web App과 대응 Sheet를 식별하고 쓰기·조회·알림 확인 범위를 확인한다. 실제 고객 데이터와 분리된 테스트 환경을 우선한다.
2. 저장소 밖 환경 설정으로 endpoint를 주입한다. 아래 명령은 **환경 확인 뒤 실행할 절차이며 이번 기록에서 실행 완료한 명령이 아니다.**

```powershell
$env:QUICK_ESTIMATE_LIVE_E2E='1'
npm run build:e2e
npx playwright test e2e/quick-estimate-live.spec.ts
```

3. 가짜 회사명은 삭제대상 표식, 이메일은 `.test` 도메인을 사용한다. 실제 연락처는 입력하지 않는다.
4. 데스크톱 마케팅 미동의와 모바일 동의 신청을 실행한다. 브라우저가 보여준 금액과 실제 POST의 금액이 일치해야 한다. 데스크톱 신청은 동일 payload를 다시 전송해 `duplicate: true`를 확인한다.

   live 브라우저 suite는 screenshot·video·trace 캡처를 끈다. 실패 시 출력에도 연락처·endpoint 원문이 있는지 확인하고 원문 로그를 PR이나 증빙에 첨부하지 않는다.

5. 생성된 `lead_id`로 테스트 행만 식별해 다음을 대조한다. 원문은 증빙 문서에 복사하지 않고 일치 여부만 남긴다.

| 대상          | 대조 기준                                                          | 현재 결과 |
| ------------- | ------------------------------------------------------------------ | --------- |
| `leads`       | 최초 신청 한 건 저장, 동일 requestId 재시도 행 수 불변             | 미검증    |
| 견적          | 업종·직원 수·금액·난수·규칙·benchmark version 일치                 | 미검증    |
| 동의          | privacy notice, marketing agreed/channels/version/accepted_at 일치 | 미검증    |
| `상담 목록`   | 동일 lead_id 한 행, 한글 업종·금액·상태·담당자 대응                | 미검증    |
| 신규 알림     | 신규 신청 알림과 접수 시각 대응, 중복 재시도 추가 알림 없음        | 미검증    |
| 알림 개인정보 | 메일에 고객 개인정보와 견적 원문 미포함                            | 미검증    |
| 테스트 정리   | 승인된 대상을 기존 파기대장 절차에 따라 정리                       | 미실행    |

6. 정리 전 대상 ID와 승인 범위를 확인하고 기존 [운영 runbook](quick-estimate-runbook.md#권한보유파기)을 따른다. 실제 고객 행은 수정·삭제하지 않는다. 행 삭제만으로 영구 파기를 주장하지 않는다.
7. 코드가 바뀌면 영향받는 검증을 갱신하고 최종 HEAD와 결과를 기록한다. live skip은 저장 성공 증거로 사용할 수 없다.

## 현재 외부 차단 조건

2026-09-04 연결된 Drive 계정은 저장소 문서에서 정한 승인 운영 계정과 일치하지 않는다. `4refund`, `간단 견적`, `환급` 검색에서 관련 테스트 Sheet를 확인하지 못했다. 연결된 브라우저에는 승인 계정의 Apps Script·Sheet 세션이 없다. 로컬에는 endpoint 설정 키가 있지만 해당 주소가 승인된 테스트 자산인지 확인되지 않았다.

필요한 조치는 승인된 테스트 Web App·Sheet의 식별, 승인 계정의 접근 연결, 알림 확인 방법과 테스트 행 정리 승인 범위 확인이다. 자격 증명은 대화·문서에 직접 전달하지 않는다. 이 조건이 해결되기 전에는 실제 저장 테스트를 실행하지 않고 RF-PR4 완료·RF-PR5 릴리스로 처리하지 않는다.

## 운영 전달 사항과 롤백

- 상담 목록과 신규 알림에는 **상세 견적 신청자만** 남는다. 계산만 한 사용자는 저장하지 않으며 신청 건수를 전체 조회 건수로 해석할 수 없다.
- 상세 견적은 상담을 통한 안내다. 회사 정보 입력 후 정밀 금액이 자동 산출되는 기능이 아니다.
- 계산·고지·payload·시트 schema와 Apps Script artifact 변경 없음. 이 프런트엔드 전환만을 위한 Apps Script 재배포나 DB migration은 없다.
- 공개 후 문제는 릴리스 변경을 revert하고 GitHub Pages 배포를 확인한다. 기존 상담 행은 변경하지 않는다. 롤백 시 연락처 우선·조회 동시 접수로 돌아가는 의미를 운영 담당자에게 알린다.
- main 병합 전 실제 저장·미해결 리뷰·필수 검사·테스트 정리 조건을 확인하고, 병합 후에는 해당 merge commit의 `verify`와 `deploy-pages` 성공 및 공개 화면 선조회를 확인한다. 공개 화면 확인을 위해 새 상담 신청을 만들지 않는다.
